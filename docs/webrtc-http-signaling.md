# WebRTC HTTP signaling relay

MAGPIE's `HttpSignaler` uses HTTP only to exchange signaling messages. Both
peers make outbound HTTP requests to one relay. The relay does not need to
understand MAGPIE, SDP, ICE, or media topics. It only knows a **session** with
at most two **participants**, and forwards opaque bytes to the other member.
The WebRTC peer connection carries all application data after the handshake.

The reusable helper in `examples/webrtc/http_signaling/` uses only the Python
standard library and has no MAGPIE import. It contains the protocol logic and
ASGI/WSGI adapters. The runnable FastAPI example is
`examples/webrtc/http_signaling_server.py`; install `fastapi uvicorn` for that
example. In `examples/webrtc/webrtc_reader.py` and
`examples/webrtc/webrtc_writer.py`, comment out the active `with_zmq(...)`
block and uncomment the `with_http(...)` block, then run both scripts in
separate terminals. The audio, video, and multimedia examples have the same
commented HTTP option.

## Wire contract, version 1

Let `base_url` be `https://host/path`, `session` the shared session ID, and
`peer` a distinct participant ID generated by each `HttpSignaler`. Each ID is
encoded as UTF-8, then unpadded URL-safe Base64, so even an ID containing `/`
remains a single path segment. The server treats these segments as opaque.
For example, `demo-call` becomes `ZGVtby1jYWxs` and `room with / slash`
becomes `cm9vbSB3aXRoIC8gc2xhc2g`. Future clients in other languages must use
the same encoding.
Requests may carry application-defined authentication headers; the hosting
application decides their meaning.

| Method and path | Meaning | Success response |
| --- | --- | --- |
| `PUT {base_url}/sessions/{session}/peers/{peer}` | Join or renew membership. Reject a third participant. | `204`; `409` when full |
| `POST {base_url}/sessions/{session}/peers/{peer}/messages` | Forward the binary body to the *other* participant. `X-Magpie-Message-Id` identifies a retry of the same send. | `204`; `404` if not registered |
| `GET {base_url}/sessions/{session}/peers/{peer}/messages?after=N&wait=S` | Wait up to `S` seconds for the first message with sequence number greater than `N`. | `200` with raw bytes and `X-Magpie-Sequence: M`; `204` on timeout; `404` if not registered |
| `DELETE {base_url}/sessions/{session}/peers/{peer}` | Leave and release the mailbox. | `204` |

The server must preserve each recipient's message order. A repeated POST with
the same `(session, peer, X-Magpie-Message-Id)` must not deliver a duplicate.
If the other participant has not joined yet, a successful POST may be dropped;
MAGPIE repeats its initial `hello` until the other peer joins.
The GET cursor provides retry safety: the server may replay the same message
until the next GET uses its sequence number in `after`. The server must not
echo messages to their sender. It can expire abandoned participants after a
lease period; the client renews membership when it receives `404`.

The request body and `200` response body use `application/octet-stream`. They
are the exact bytes from `WebRtcSignaler.publish`; no JSON envelope or SDP
parsing is required on the server. An HTTP implementation may use in-memory
queues for a single instance or shared storage for multiple instances. The
reference relay is intentionally in-memory. The FastAPI example supports an
optional bearer token for a local demonstration (`MAGPIE_SIGNAL_TOKEN`).
The FastAPI example allows browser origins on `localhost` and `127.0.0.1` by
default. Set `MAGPIE_SIGNAL_ALLOWED_ORIGINS` to a comma-separated list of
other allowed origins when hosting a browser client elsewhere. It handles CORS
preflight requests and exposes `X-Magpie-Sequence` to browser JavaScript.
Production identity, authorization, TLS termination, and shared storage belong
to the hosting service.

## Reusing the Python server helper

Copy `examples/webrtc/http_signaling/` into the web application. Its
`SignalingHTTP` class handles all four methods and response codes, while
`SignalingASGI` and `SignalingWSGI` translate standard web requests and
responses. For example, an existing ASGI app can mount the complete relay:

```python
from http_signaling import InMemoryRelay, SignalingASGI, SignalingHTTP

app.mount("/signal", SignalingASGI(SignalingHTTP(InMemoryRelay())))
```

The runnable FastAPI example shows this setup. A Flask application can mount
the WSGI adapter using Werkzeug, which Flask already uses:

```python
from werkzeug.middleware.dispatcher import DispatcherMiddleware
from http_signaling import InMemoryRelay, SignalingHTTP, SignalingWSGI

signaling = SignalingWSGI(SignalingHTTP(InMemoryRelay()))
flask_app.wsgi_app = DispatcherMiddleware(
    flask_app.wsgi_app, {"/signal": signaling}
)
```

The host must authenticate and authorize session access before forwarding a
request to either adapter. Flask route decorators do not protect a mounted
WSGI sub-application; use middleware around the signaling app. An in-memory
relay only works in one process. Azure Functions can host the ASGI adapter,
but scaled Functions or multiple web workers need a shared implementation of
the same `join`, `send`, `receive`, and `leave` operations. The adapters do not
parse MAGPIE `hello`, SDP, or ICE.

## Python client

All seven `magpie-*-webrtc` command-line tools also accept an HTTP or HTTPS
relay URL. For example, after starting the relay, run these in separate
terminals with the same session ID:

```bash
magpie-read-webrtc demo /robot/state --signaling http://127.0.0.1:8000/signal
magpie-write-webrtc demo /robot/state '{"count":1}' --signaling http://127.0.0.1:8000/signal
```

Use `--http-headers @headers.json` on both commands if the host requires
authentication. The file must be a JSON object of string headers, for example
`{"Authorization":"Bearer TOKEN"}`. `--timeout` sets the HTTP request timeout;
the default is 10 seconds. CLI headers are fixed for the life of the process.
For expiring tokens or custom HTTP clients, use the Python API below.

```python
from luxai.magpie.transport.webrtc import WebRTCConnection

conn = WebRTCConnection.with_http(
    "https://signal.example.com/webrtc",
    session_id="call-123",
    headers={"X-Tenant": "team-a"},
    headers_provider=lambda: {"Authorization": f"Bearer {get_token()}"},
    reconnect=True,
)
conn.connect(timeout=30)
```

`headers_provider` is called before each join, send, poll, and leave request,
so it can return a refreshed token. The send and poll workers may call it
concurrently. Its fields override `headers`. A supplied
`http_client` is borrowed rather than closed; it can carry custom TLS, proxy,
cookie, or authentication behavior. The default HTTP client is `httpx`,
installed by `pip install "luxai-magpie[webrtc]"`.

`publish` queues the outgoing message. Separate worker threads perform HTTP
POSTs and long polls, keeping network waits off the aiortc event loop. A
failed POST is retried with the same message ID and order is preserved. The
same `WebRTCConnection` stream and RPC classes work without changes.
